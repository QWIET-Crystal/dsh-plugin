`wmi=denied` 那一趟的 `live=7` 是退化模式的副作用：拿不到命令行，它把**所有** node 进程当候选逐一评估
（保护端口 3080/19372/43120 仍在保护列表里，且 `-AllowDegradedKill` 默认关，所以只报告不误杀）。

## 判定签名

没人能一眼看出来：**守护"在跑"但已经退化或停摆**。判据：

1. 守护日志出现 `wmi=denied`（受限令牌拿不到 `Win32_Process`，退化成弱启发式）；
2. `_probe\guard-task.log` 心跳**不再推进**，但守护进程看着还在；
3. 查守护的父进程：它是由**代理会话内**启动的（继承了沙箱作业，随时会被回收）。

## 根因

**两条，都已验证：**

1. **代理会话内启动的进程会继承文件沙箱**，后果有两个，缺一不可地解释了现象：
   - 受限令牌导致 `Get-CimInstance Win32_Process` 拿不到数据 → 守护自称 `wmi=denied`，退化成弱启发式；
   - 整棵进程树被放进该次工具调用的**作业对象**，作业关闭时被回收 → pid 548 消失。
   → 结论：**常驻守护不能从代理会话里启动**，必须像登录时那样在不受限上下文里拉起。
   这也是为什么「重启守护」这一步交给用户双击（或管理员计划任务）才是稳的。

2. **按命令行匹配杀进程会误杀自己**：我用
   `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match 'dsh-guard-loop' }`
   去清残留，而**正在执行这条命令的那个 shell 自身命令行里就含这个字符串**，于是它匹配到自己、
   把自己 Stop-Process 掉，该次调用以 `exit code: 4294967295`(-1) 中断、后续步骤全部没执行。
   → 结论：**要用「日志里记的 pid」去核对身份，不要用命令行字符串匹配**，除非把匹配串做拼接
   （如 `'dsh-guard-' + 'loop'`）以免自匹配。

## 处置与结果

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | `Stop-Process 22768` 停掉老循环 | 成功，但引入了后续风险（当时的新循环还没站稳） |
| 2 | 从会话内经 vbs 启动新循环 | 启动成功但**降级**，780 秒内无人察觉的隐患 |
| 3 | 读日志取 `loop starting` 的 pid 复核存活 | 发现 pid 548 已死 → 确认「无守护」 |
| 4 | 提权（`danger-full-access`）重启守护 | pid 45176，`wmi=ok`，两守护均正常推进 |
