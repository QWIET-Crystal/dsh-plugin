## 判定签名

> ⚠️ 这一条是**症状**，不是独立根因（真上游见 `2026-09-24-gpu-process-crash`）。

1. 页面无响应/卡顿，**但后端接口仍然秒回**；
2. 某个渲染进程 CPU 长时间贴近单核上限；
3. **判据的分水岭**：杀掉之后是否换进程继续烧 —— 换 = 上游（GPU 崩溃→软件渲染）没解决；不换 = 可能只是本次卡死。

## 根因

> ⚠️ **本条目的根因已被修正。** 下面是当时的判断，**不是最终结论**，保留以供复盘。
> 真正上游见 [`2026-09-24-gpu-process-crash.md`](2026-09-24-gpu-process-crash.md)：
> **GPU 子进程在 14:16:06 崩溃后回退到软件渲染**，渲染进程在替显卡干活，所以 CPU 狂烧。
> 判定依据：崩溃后**换了一个进程继续烧**（16572 → msedge 2812），说明上游没解决。

当时写下的（症状级推测）：

渲染层进入死循环 + 内存泄漏。CPU 逐小时爬升（25% → 57% → 63%）与工作集反复冲高回落（GC 抖动）
是同一现象的两面：某个循环在不断分配对象。属 Electron / 浏览器渲染层问题，**不是 DSH 后端逻辑**。

**这次误判的教训**：CPU 与内存指标只能告诉你"哪里不对"，**告诉不了你"为什么"**。
要拿上游原因，必须去读**应用自己的日志**（`%APPDATA%\DSH Desktop\logs\`）——
这正是 doctor 事后新增的一步检查。

## 处置与结果

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 分层取证：后端 HTTP、端口、进程、资源 | 确认后端健康、问题在渲染层 |
| 2 | 建议在卡住窗口 `Ctrl+R` 重载界面 | 推荐路径（释放 JS 堆 + 终止循环，宿主不受影响） |
| 3 | 明确**不**建议直接重启 DSH Desktop | 代价大：打断宿在其内的所有正在跑的回合 |

## 教训

**"页面无响应" 有两个完全不同的成因，处置代价差十倍**，必须先分清：

| 成因 | 判定 | 处置代价 |
|---|---|---|
| 渲染层卡住（本故障） | 子进程高 CPU / 内存暴涨，**但宿主 HTTP 秒回** | Ctrl+R 重载窗口，不打断任何会话 |
| 宿主进程死亡（`#前端进程死亡`） | 端口无监听、进程不存在 | 必须重启应用，打断所有会话 |

而且**后端秒回恰恰会掩盖渲染层故障** —— 只测 HTTP 会得出"一切正常"的错误结论。
