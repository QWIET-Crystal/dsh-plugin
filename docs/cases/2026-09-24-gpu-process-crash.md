# GPU 子进程崩溃 → 软件渲染回退 · 2026-09-24

- **首次发现**：2026-09-24 17:06（体检报告 `:3080` 无监听时，顺藤摸到 DSH Desktop 日志）
- **崩溃时刻**：2026-09-24 14:16:06
- **现象**：页面无响应；后端却一直秒回；某个渲染进程持续烧 CPU，且**换一个进程继续烧**
- **影响**：界面卡顿/不可用、CPU 被白白烧掉、`:3080` 网页端反复死亡
- **最终归类**：`对策库 #GPU进程崩溃`（上游） + `#渲染层失控`（表现）

## 证据原文

**破案的关键一行** —— DSH Desktop 自己的日志（`%APPDATA%\DSH Desktop\logs\dsh-2026-09-24.log` 全文只有三行）：

```
--- dsh-plugin-desktop DSH Desktop 2.0.4 win32 node v24.18.1 run 1790210737686 ---
dsh-plugin-desktop: previous desktop run did not shut down cleanly (startedAt: 2026-09-23T11:34:12.468Z, pid: 40368, version: 2.0.4)
dsh-plugin-desktop: child process gone (type: GPU, service: GPU, reason: crashed, exitCode: 34 / 0x00000022)
```

**渲染进程烧核**（同一个病，换了对象）：

```
13:44  DSH Desktop 16572  占用一路 25% -> 57% -> 63%
16:10  DSH Desktop 16572  63.4% 单核，工作集 814MB，10 秒内增长 103.6MB
17:06  msedge 2812        77.8% 单核，启动 16:05:14，一小时累计 595 秒 CPU
```

**后端始终健康**（这是最容易误导人的地方）：

```
http://127.0.0.1:43120/ -> 401 in 46ms
http://127.0.0.1:3080/  -> 200 in 12ms   （14:15 时；16:00 起连接被拒）
```

**排除驱动层**：系统日志 8 小时内无显示驱动 TDR/重置事件，只有信息级的显示配置变更。

## 根因

**GPU 子进程崩溃后，Chromium 系应用回退到软件渲染**，把光栅化/合成/动画全部改由 CPU 计算。
于是出现了那个此前完全讲不通的组合：**后端 HTTP 秒回、同时有进程烧 60~80% 的核**。
业务逻辑与渲染无关，所以后端毫发无伤；渲染进程在替显卡干活，所以 CPU 狂烧。

## 归因边界（必须写清）

`GPU 进程崩溃` 与 `:3080 网页端反复死亡` 时间上高度重合，但**没有直接证据证明前者导致后者**。
已证实的是：GPU 崩了（应用日志）、外壳崩了（系统事件日志）、渲染在烧核（进程采样）、`:3080` 没了（端口探测）。
四件事挤在同一分钟，很可能是同一个上游事件（显示/会话层变动）的不同后果。
**不做因果断言**；重启 DSH Desktop 可同时验证这两条。

## 处置与结果

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 分层取证 | 确认后端健康、问题在渲染层 |
| 2 | 读 DSH Desktop 日志 | **找到 GPU 崩溃原文**（本次破案点） |
| 3 | 排除驱动 TDR | 系统日志无重置事件，判定为应用侧 |
| 4 | 判定处置 | 需重启 DSH Desktop 让 GPU 进程重生——**重载窗口救不了** |

## 教训

**"重载窗口" 与 "重启应用" 的分界线，就在这里：**

| 现象 | 上游 | 正确处置 |
|---|---|---|
| 同一个渲染进程烧核，重载后不再犯 | 该进程自身状态坏了 | Ctrl+R 重载窗口（不打断任何会话） |
| 重载后**换个进程继续烧** | GPU 子进程已死，软件渲染兜底 | 必须重启应用，让 GPU 进程重生 |

这也是为什么**只盯进程指标会误判**：我一度把它诊断为"死循环 + 内存泄漏"，那是症状级推测；
真正的原因要读**应用自己的日志**才能拿到。doctor 因此新增了"读 DSH Desktop 日志做上游归因"这一步。
